# Ticket Brief

한 가지만 합니다. 배경·문제·As-is·PRD가 정한 방향을 정리합니다. 해결안은 만들지 않고(`decision-prototype`), PRD를 고치지 않습니다(`prd-fill`).

## Operating Posture

다음 단계의 사람이 이 보고서만 읽고 "무엇이 문제이고, 무엇이 아직 정해지지 않았는지" 알 수 있어야 합니다.
문제 정의는 PRD 문장을 옮기는 것이 아니라, 화면과 코드에서 확인한 사실로 다시 씁니다.

## Hard Rules

1. **진입 경로를 전부 연다.** 같은 값을 바꿀 수 있는 곳(인라인 입력, 수정 패널, 다이얼로그)을 모두 열어 캡처한다. 코드만 읽고 "어디에도 없다"고 쓰지 않는다.
2. **동작은 상태별로 코드에서 확인한다.** 예: 진행중, 일시 정지, 재개 후. 확인한 경로(`file:line`)를 남기고, 확인하지 않은 상태는 추정이라고 적는다.
3. **운영 화면은 저장하지 않는다.** `screen-capture` 절차를 따르고, 데이터가 그대로인지 확인한 결과를 보고서에 적는다.
4. **PRD가 정하지 않은 것은 '결정 필요'로만 적는다.** 답을 미리 정하지 않는다.
5. **사람의 말은 그 사람의 표현으로 인용한다.** 요청자가 문의를 어떻게 나눴는지가 범위를 정한다.

## Workflow

### Phase 1 — 출처 모으기
[SOURCES.md](SOURCES.md) 순서대로 본다: 이슈 → 이슈에 걸린 채팅 스레드 → PRD(탭·하위 블록 포함) → PRD에 연결된 고객 요청 → 이전 작업 로그.
**완료 기준**: 요청자, 요청 경로, PRD의 배경·문제 정의·목표(비어 있으면 비어 있다고)를 한 줄씩 적을 수 있다.

### Phase 2 — 코드로 동작 확인
화면 → 데이터 로드 → 저장 → 실제로 일어나는 일(발송, 재개 등)까지 따라간다. 상태가 갈리면 상태마다 따로 본다.
**완료 기준**: "사용자가 X를 하면 Y가 된다"를 상태별로 쓸 수 있다.

### Phase 3 — As-is 캡처
문제가 실제로 일어날 수 있는 데이터가 있는 예시를 고른다(예: 등록 고객이 남아 있는 시퀀스). Phase 2에서 찾은 진입 경로를 모두 연다.
**완료 기준**: 진입 경로마다 캡처가 있고, 데이터가 그대로라는 확인이 있다.

### Phase 4 — 보고서
`html-report`로 만든다. 구성: 요약 3줄 → 배경(타임라인) → 동작 원리 → As-is → 문제 → PRD에 적힌 해결 방향 → 결정 필요.
**완료 기준**: 게시본 링크를 사용자에게 줬다.
