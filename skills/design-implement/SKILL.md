# Design Implement

한 가지만 합니다. 정해진 디자인을 코드로 옮기고 로컬에서 확인합니다. 설계를 바꾸지 않고(`decision-prototype`으로 돌아감), 레포의 PR·리뷰 절차를 대신하지 않습니다.

## Operating Posture

제품 레포의 에이전트 규칙(`CLAUDE.md`, `AGENTS.md`, 레포 안의 스킬)이 이 스킬보다 우선합니다. 이 스킬은 디자이너가 그 규칙을 따라
구현할 때의 순서와, 레포 문서에 없는 로컬 함정을 다룹니다. 가장 짧은 diff가 기본값입니다.

## Hard Rules

1. **레포 메모를 먼저 읽는다.** 이 저장소의 `local/<레포 이름>.md`가 있으면 읽는다. 없으면 [REPO-NOTES.example.md](REPO-NOTES.example.md) 형식으로 만들면서 진행한다.
2. **worktree에서만 작업한다.** 메인 폴더는 다른 세션이 쓸 수 있다. 브랜치 이름은 이슈 트래커가 정한 이름을 쓴다.
3. **레포의 리뷰·PR 스킬은 복사하지 않고 부른다.** 이 스킬은 언제 부르는지만 정한다.
4. **계획 승인 전에는 소스를 편집하지 않는다.**
5. **운영 데이터를 바꾸지 않는다.** 로컬 확인용 데이터는 로컬 DB에만 넣고 끝나면 지운다.
6. **확인하지 못한 경로는 확인하지 못했다고 쓴다.** PR 체크리스트에 남긴다.

## Workflow

### Phase 1 — 브랜치와 작업 메모
이슈의 브랜치 이름 확인 → `git worktree add ../<레포>-<티켓> -b <branch> origin/<base>` → 레포 메모의 의존성 연결 절차 →
레포가 요구하는 작업 메모(todo 등)와 대상 파일 목록, 그 파일에 걸린 레포 규칙 문서 읽기.
**완료 기준**: 현재 브랜치가 이슈 브랜치와 같고, 대상 파일에 해당하는 규칙 문서를 다 읽었다.

### Phase 2 — 조사와 계획
화면 → 데이터 로드 → 컴포넌트 → 저장·후속 동작까지 따라간다. 새 조회·변경 로직이 생기면 레포의 구현 전 리뷰 스킬을 서브에이전트로 돌리고,
지적을 계획에 반영한다. 계획은 승인을 받는다(plan mode 등).
**완료 기준**: 사용자가 계획을 승인했다.

### Phase 3 — 구현
기존 컴포넌트를 먼저 찾는다. 새 파일은 문구·조합용 얇은 감싸개까지만. 쿼리를 추가했으면 쿼리 의미를 지키는 테스트를 분기당 1개 쓴다.
**완료 기준**: typecheck 통과, 변경 파일 lint 오류 0, 새 테스트 통과.

### Phase 4 — 로컬 확인
레포 메모대로 dev 서버를 띄우고, 계획의 시나리오를 하나씩 확인한다. 결과는 숫자(배너 개수 등)로 남긴다.
줄바꿈, 구분선처럼 눈으로만 보이는 문제는 캡처를 보고 고친다.
**완료 기준**: 시나리오를 모두 확인했거나 미확인 사유를 적었다. 구현 캡처를 저장했다.

### Phase 5 — 넘기기
`impl-report`로 보고서, `prd-fill`로 PRD를 구현과 맞춘다. PR은 레포의 PR 스킬로 만든다. 끝나면 dev 서버를 끄고 로컬 데이터를 지운다.
