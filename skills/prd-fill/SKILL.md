# PRD Fill

한 가지만 합니다. 이미 있는 PRD에 정해진 내용을 옮깁니다. 새 결정을 만들지 않고, 새 PRD를 쓰지 않습니다.

## Hard Rules

1. **작성자 문장은 고치지 않는다.** 배경·문제 정의는 그대로 두고, 빈 칸과 내가 쓴 칸만 채운다.
2. **정한 것만 쓴다.** 대화에서 사용자가 정했거나 코드로 확인한 것만. 미정은 '결정 필요'로 남긴다.
3. **엣지케이스는 동작을 바꾸는 것만.** 방어 규칙, 구현 세부(연타 방지 등)는 쓰지 않는다.
4. **구현과 다르면 PRD를 고친다.** 구현 후에는 PRD 문장을 실제 동작과 한 줄씩 대조한다. 예: "패널을 열기만 하면 표시하지 않는다"가 이미 수정한 스텝에서는 틀리면 조건을 나눠 쓴다.
5. **화면 요소는 화면에 표시된 이름으로 부른다.** 아이콘 모양("연필")이 아니라 기능 이름("수정 버튼").
6. **문서 도구의 실제 저장 형태로 찾아 바꾼다.** 표 안의 `>`처럼 저장 형태가 다를 수 있으니, 바꾸기 전에 문서를 다시 읽고 그 문자열을 쓴다.

## Workflow

1. **읽기**: PRD 전체를 읽는다. 탭, 표, 체크리스트, 속성(이슈 번호·링크·연결된 고객 요청)까지.
2. **대조**: 지금까지 정한 것을 칸별로 나눈다.

   | 칸 | 넣을 것 |
   |---|---|
   | 목표 | 무엇을 알게 하는지, 범위에서 뺀 것 |
   | 유저 시나리오 | 대표 경로 하나를 3~4단계로 |
   | 엣지케이스 | 동작이 달라지는 조건 |
   | 기능 명세 표 | 화면/영역 · 사용자 행동 · 시스템 동작 · 조건/예외 · 비고 |
   | 디자인 | 필요한 화면, 사용할 기존 컴포넌트와 상태, 위치 이유, 레퍼런스 링크 |
   | 속성 | 이슈 번호와 링크 |

3. **반영**: 칸 단위로 작게 바꾼다. 경고가 나면 다시 읽고 고친다.
4. **보고**: 바꾼 칸과 이유, 바꾸지 않은 칸을 짧게 말한다.
