# Decision Prototype

한 가지만 합니다. 조사가 끝난 문제에 대해, 사용자가 눌러 보며 결정할 수 있는 HTML을 만듭니다.
코드를 고치지 않고(`design-implement`), 조사하지 않습니다(`ticket-brief`).

## Operating Posture

목적은 **결정**입니다. 예쁜 시안이 아니라, 여는 사람이 "이 경우엔 이게 나오는구나"를 눌러서 확인하고 고르게 하는 도구입니다.
결정이 끝난 축은 바로 지웁니다. 남겨 두면 다음 사람이 무엇이 확정인지 모릅니다.

## Hard Rules

1. **틀은 [HARNESS.md](HARNESS.md)를 그대로 복사한다.** 컨트롤 바, 프레임, '어떤 경우에 무엇이 나오나', '보는 법'의 마크업과 CSS를 바꾸지 않는다.
2. **제품의 디자인 토큰만 쓴다.** 세일즈맵이면 [salesmap.kr/design/token.md](https://salesmap.kr/design/token.md). 프레임 안 컴포넌트는 제품 코드의 실제 모양을 따른다.
3. **운영 화면을 옮긴다.** 프레임 안은 As-is 캡처와 같은 구조·문구·크기. 예시 데이터는 캡처에 있던 이름과 숫자를 쓴다.
4. **토글은 아직 정하지 않은 축만 둔다.** '현재 / 제안'은 항상 둔다. 사용자가 정한 축은 토글과 비교 표를 지운다.
5. **위치는 스크롤한 상태로 확인한다.** 안내·배너 위치는 맨 위 항목이 아니라 뒤쪽 항목을 고치는 상태로 캡처해 본다.
6. **표와 동작은 같은 데이터로 만든다.** 동작을 바꾸면 '어떤 경우에' 표도 같은 턴에 고친다.
7. **엣지케이스를 덧붙이지 않는다.** 조건 표는 사용자가 판단할 분기만 담는다.

## Workflow

### Phase 1 — 범위
화면 하나, 결정할 것 한 문장. 예: "등록 고객이 있는 시퀀스를 수정할 때 안내를 어디에, 언제 띄울지".
**완료 기준**: 결정할 축과 각 축의 후보가 정해졌다.

### Phase 2 — 운영 화면 옮기기
As-is 캡처를 보고 프레임을 만든다. 없으면 `screen-capture`로 먼저 찍는다.
**완료 기준**: '현재'를 고르면 운영 화면과 같게 동작한다.

### Phase 3 — 제안과 토글
추천안에 `추천` 표시를 단다. 상태 데이터(대상 0명, 1명 이상, 여러 상태가 섞임)를 바꾸는 토글을 둔다.
**완료 기준**: 모든 조합이 동작하고, 표와 프로토타입이 같은 결과를 보여 준다.

### Phase 4 — 게시와 확인
`YYYYMMDD-<티켓>-<주제>.html`로 저장하고 게시한다. 게시본을 열어 핵심 시나리오를 눌러 보고 캡처를 보여 준다.
**완료 기준**: 사용자가 캡처로 동작을 확인했다.

### Phase 5 — 피드백 반영
피드백마다 바뀐 점을 한 줄씩 말하고 같은 주소로 다시 게시한다. 결정된 축은 토글과 비교 표를 지운다.
